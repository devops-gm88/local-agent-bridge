Shotty

A page on your phone that answers from your own notes — and can make one gated change. Not DSH. Not Mark.

What it actually is

You type something on your phone. The page sends it to a small program running on your Mac. That program looks through the notes in ~/Workspace/MARK, then asks a small AI model on the Mac (qwen2.5:7b, via Ollama) to answer using only what it found.

It has three tools: count the rows in its local rows sheet, total a numeric field, and append a row. The model chooses the tool itself. The append is a write: it never runs when requested — it waits for you to tap Approve on the page.

Nothing is sent to the internet. There is no cloud, no API key, no account.

It cites the file and line it used. If the notes don't contain the answer, it says so.

What it is not

  • It is not DSH — the assistant you talk to at 127.0.0.1:3080. That one edits files and runs commands. This one reads notes and can append a row, with your approval.
  • It cannot change anything without you. A write opens an approval card; nothing is written until you tap Approve, and it executes exactly once. A second tap is a no-op.
  • It does not move Mark anywhere. It reads the MARK folder where it already is.

Approvals — the one place it can change something

Ask it to append a row and the reply will say it needs your approval. Above the reply you get a card with the tool name, the exact row it wants to write, and two buttons:

  • Approve — executes the write, once. The card says “Approved — executed exactly once.”
  • Reject — records the refusal and writes nothing. “Rejected — nothing was executed.”
  • Other actions (e.g. Replace / Drop for research, Accept / Dispute for reconciliation) — the card shows the buttons that workflow defines, and the decision is sent back to the workflow. “Replace — recorded and sent to the workflow.”

Both decisions are appended to state/approvals.jsonl. If the page is reloaded — or left open, it checks every 10 seconds — pending approvals are fetched and shown, with the count in the title. Tapping Approve twice (or reopening the link) cannot write twice — the id is bound to the run id and a hash of the payload.

The four commands you actually need

1 · Start it (and keep it running forever)

cd ~/Workspace/MARK/Projects/Job_Search/bridge
./install-service.sh

One time only. After this it starts by itself at login, restarts if it crashes, and closing Terminal does nothing. On a laptop the Mac must be awake for the phone to reach it.

2 · Give it a name

cd ~/Workspace/MARK/Projects/Job_Search/bridge
echo Shotty > state/name
./install-service.sh

Replace Shotty with whatever you want. That is the name it uses for itself.

3 · Get the link for the phone

cd ~/Workspace/MARK/Projects/Job_Search/bridge
./phone.sh

Prints the address and the token, copies the link to your clipboard, and draws a QR code you can scan with the phone camera. The address and token are stable now — once you add it to the Home Screen it keeps working.

4 · Stop it

cd ~/Workspace/MARK/Projects/Job_Search/bridge
./uninstall-service.sh

Stops it and removes the auto-start. Your notes and settings are untouched.

What it can and cannot answer

Good at: one-hop lookups. “Did we apply to the aged care job?”, “What is the next action on the local agent?”, “Why did we skip the ad-intelligence job?” It can also walk its own tools in sequence — count the rows, total the amount, then report both.

Weaker at: questions that need several documents joined together, or anything not written down in ~/Workspace. The 7b model occasionally answers a tool request in prose instead of calling the tool; if that happens, ask again with “call the tool”.

Under the hood, in one paragraph

A Node server (server.js) serves the page and answers POST /task. Before answering it searches a local index of about 900 chunks from 39 markdown files (context.js) and puts the best few in the prompt, with instructions to refuse when they don’t contain the answer. The model is Ollama on localhost:11434. It is handed the tool list (the same definitions are served over MCP by mcp_server.js); if it calls a read, the result goes back into the loop until it answers. A write opens an approval instead. At 18:00 local a deterministic end-of-day summary is written from the logs. Everything is stored under bridge/state/: token, name, run log, approvals, conversation memory, summaries.
